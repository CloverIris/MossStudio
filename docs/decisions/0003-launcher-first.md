# ADR-0003：V1 不做自有推理引擎，启动器先做“运行时编排器”

- 影响：ADR-0001（macOS 选 MNN）保留为**未来引擎**的技术结论，但**不在 V1 排期**。

## 背景

最初立项把“脱离 torch 的推理引擎”当作核心。但产品要解决的第一性问题其实是：

1. 用户装不上、跑不起来、不知道自己的机器能不能跑；
2. 多个版本/分支互相打架；
3. 权重下载、LoRA 管理、报错排查全靠命令行；
4. 官方更新了不知道。

这些问题**不需要自研推理后端**就能解决，而且解决它们才能拿到真实用户与真实日志，
反过来决定引擎该优化什么。

## 决策

V1 的引擎就是**外部 Python 运行时**：

- 官方 `gradio_app.py`（Gradio 适配器）；
- 我们随应用分发的**薄 runner**（`runner.py`，调用官方 pipeline，输出 NDJSON 事件）；
- 两者都通过同一个 Supervisor 管理，stdout/stderr 走同一套解析管线。

V1 **不实现**：模型图、kernel、量化运行时、VAE 解码器、采样器。

薄 runner 的边界：只做“加载官方 pipeline + 循环采样 + 发事件”，不复制模型结构、
不改数值；它 ≤ 300 行，随启动器版本走，可被官方代码升级影响。

## 后果

**正面**

- 两周内能跑通“安装 → 环境报告 → 实例 → 下载 → 生成 → 进度/报错”闭环；
- 不背 27 GB 权重与 MNN 图的转换负担，先把产品体验做对；
- 用户机器上的真实日志 + 真实失败模式，成为未来引擎的验收集；
- 训练器桥接、模型管理器等模块与推理后端解耦，未来换引擎不动上层。

**负面**

- 仍然依赖 Python/torch，安装体积大、启动慢；
- macOS 上 50 步依旧很慢（这是模型本身的性质，不是启动器能解决的）；
- 薄 runner 需要跟随官方仓库的接口变化维护。

**风险缓解**

- 实例固定 commit，官方破坏性变更不会影响已装实例；
- runner 协议独立于官方代码，接口变化只改一个适配层；
- 未来引擎（ADR-0001）通过 `RuntimeAdapter` 接口插入，UI 与协议不变。

## 与 ADR-0001 的关系

ADR-0001 的结论（MNN 为主、MPS 仅 oracle、MLX 条件触发）仍然有效，
但触发时间改为 **V2**：当启动器积累了足够的真实设备数据、且用户明确抱怨性能时，
再启动 M0 spike。MNN 相关文档保留在
[future-inference-engine.md](../archive/future-inference-engine.md)，不删除。
