# GPU 设备管理、性能推荐与多卡 Canvas 调度

- 状态：实施中（自动 GPU 调度与逐卡引擎 probe 已落地；真实异构双卡硬件验收待完成）
- 日期：2026-11-01
- 关联：[Studio 多 Canvas Project 设计](./multi-canvas-studio.md)
- 范围：本机 NVIDIA GPU 枚举、架构感知的引擎选择、推理设备设置、OOBE/引擎页 UX、标题栏状态与按 GPU 调度 Canvas 推理任务

## 当前实现进度

- 已实现：启动后台扫描 NVIDIA GPU；采集 UUID、当前 index、名称、显存、利用率、驱动版本及驱动可提供的 compute capability；探测状态/错误通过 IPC 与事件展示。
- 已实现：按可识别的 compute capability、显存与 index 生成可复现的推荐设备；默认 UUID 选择和显存策略偏好持久化；引擎页/OOBE 显示设备清单，允许手动设默认卡与重新扫描。
- 已实现：自动架构安装不再从当前引擎猜测；读取选定 GPU 的独立清单，未知架构或无明确设备时拒绝自动选包，安装后以 UUID 重新解析 index 并要求新引擎 probe 明确支持目标 GPU。
- 已实现（Phase 2）：Canvas 可保存 GPU UUID；Studio 提供“跟随应用默认/指定 GPU”，提交时以 UUID 固定设备，并在 Job 快照中保留设备名与当次 index。GPU UUID 在线但 ordinal 变化时按 UUID 重新解析；绑定设备缺失时显式失败。每个 Canvas 阻止重复活动任务。
- 已实现（Phase 2）：本机每个 GPU UUID 有独立 MossInfer sidecar 与队列；Supervisor 按 GPU UUID 串行调度同卡任务、并行启动不同卡任务。进程崩溃、超时与取消重启限制在对应 GPU runtime；远端按 hostId 独立排队。
- 已实现（Phase 3）：逐卡 memory/tier 覆盖和 Job 策略快照；主进程统一 GPU 遥测；Studio 标题栏摘要与展开详情。
- 已实现：自动 GPU 提交只考虑当前引擎 probe 明确支持的 GPU；优先选推荐顺序中的空闲卡，全部繁忙时选负载最低者，并在入队时固定 UUID。用户/Canvas 手动绑定不自动漂移。
- 已实现：引擎页显示每张 GPU 的兼容/不兼容/待测状态，并可触发 hello probe；未知或不支持卡不会被自动调度。
- 显存策略：自动模式下仅对总显存低于 6 GiB 的卡推荐省显存；6 GiB 及以上默认均衡，24 GiB 及以上推荐速度优先。未知显存时沿用全局设置。
- 仍待实现：设备热插拔/驱动重置主动监听、按 GPU 绑定不同引擎版本；设备变化仍依赖刷新、启动探测和任务提交校验。
- 验证边界：现有自动测试与 fake server 验证运行链路；当前硬件仅有单卡，双卡并行仍需在多 GPU 机器上实测。
- 验证边界：单元测试覆盖 inventory 解析、推荐排序和 SM75/标准架构判定；目标 Windows NVIDIA 硬件的完整安装与真实推理仍需实机验收。

## 1. 背景与问题

当前 GPU 信息来自不同的临时路径：环境扫描只取一个 GPU，设备页用 `nvidia-smi` 枚举 CUDA ordinal，MossInfer `hello` 才提供 compute capability 和引擎兼容性。引擎下载的“自动架构”又依赖当前引擎的探测结果。首次安装、旧引擎不报告完整设备信息或多卡架构不同时，这些信息可能不完整，最终把普通 SM80+ 包误当成适用于 SM75 的包。

设计实施前，任务缺少统一的设备所有权：Canvas 可携带设备字符串，但本机 MossInfer 只有一个共享 sidecar 和 FIFO 队列。设备编号若直接持久化为 `cuda:0`，GPU 枚举变化后可能静默指向另一张卡。

本设计将 GPU 作为应用级资源统一建模，使设备探测、引擎兼容、用户选择、性能建议、任务绑定和运行状态有一致的数据来源。

## 2. 目标与非目标

### 目标

1. 启动后扫描全部本机 NVIDIA GPU，呈现型号、稳定身份、CUDA ordinal、SM 能力、总/可用显存、引擎兼容状态。
2. 多卡机器默认推荐兼容且综合性能最强的 GPU；同型号同能力时稳定选择 CUDA index 最小者。用户始终可以覆盖。
3. 架构选择与实际 GPU 清单绑定。SM75/RTX 20 不得下载或激活普通 SM80+ 包；自动探测不确定时不能静默回退到标准包。
4. 按硬件提出显存使用/性能建议，在 OOBE、引擎页和标题栏持续说明当前选择；建议与用户覆盖都可持久化。
5. 一个 Canvas 的单个推理任务只绑定一张 GPU。每张 GPU 同时最多运行一个本地 MossInfer 任务；N 张可用 GPU 最多运行 N 个任务。
6. 将设备选择以稳定 GPU UUID 保存，运行时才解析成引擎所需的当前 ordinal。
7. 自动建议不能静默更改模型、权重精度、量化精度、数据类型或 Canvas 的生成参数。

### 非目标

- 自动超频、风扇/功耗控制、驱动安装或 CUDA Toolkit 管理。
- 自动修改模型精度、量化或替用户替换模型组件。
- 将本机 GPU 并发承诺扩展到 SSH 主机；远端仍按各主机独立设备与调度策略处理。
- 根据 GPU 使用率波动自动抢占或迁移正在运行的任务。

## 3. 核心原则

- **设备身份不等于 ordinal**：UUID 是持久化身份；`cuda:N` 只在本次枚举/进程环境中有效。
- **一个事实来源、分层校验**：系统探测提供硬件清单，所选 MossInfer 二进制提供运行时兼容报告；两者都需要记录，不能把其中一个当作另一个的替代。
- **兼容优先于推荐性能**：不支持该 SM 的引擎不得启动任务；架构未知时明确显示“待验证”，不得当作兼容。
- **自动是可解释、可撤销的**：显示推荐原因和来源；用户改选后保存为明确覆盖值。
- **显存模式与精度分离**：自动策略仅调整显存/执行模式；绝不改写模型权重精度或量化，也不静默改写 Canvas 的分辨率、步数、CFG、seed 或 base/dmd8 参数。
- **资源槽位由主进程拥有**：Renderer 只提交意图和显示状态，不能自行并发启动引擎。

## 4. GPU Inventory 与探测生命周期

### 4.1 设备记录

主进程维护一个带时间戳的本机 GPU inventory。每个 NVIDIA 设备至少包括：

| 字段 | 用途 |
|---|---|
| `uuid` | 持久身份，绑定 Canvas、用户默认项和设备偏好 |
| `index` | 当前系统/CUDA ordinal，只供当前进程启动与日志显示 |
| `name` | 型号、UI 展示及同型号判断 |
| `computeCapability` | major/minor；来自系统探测，并由 MossInfer hello 校验 |
| `memoryTotalBytes` / `memoryFreeBytes` | 能力评估与显存建议；free 值带采集时间 |
| `utilizationPercent` | 状态展示和调度提示，不用于改变绑定 |
| `driverVersion` | 诊断和引擎兼容提示 |
| `engineCompatibility` | 对每个已知引擎路径的 `supported/unsupported/unknown` 与原因 |

不支持 CUDA 的设备可以继续在系统设备列表中展示，但不进入本地 MossInfer GPU 执行槽位。

### 4.2 探测流程

1. 应用启动后由主进程异步刷新本机 GPU 清单；不阻塞窗口显示，也不要求用户先打开引擎页。
2. 先使用系统 NVIDIA 接口枚举 UUID、index、名称、显存、驱动、利用率和可获得的 SM 能力。
3. 若有可执行 MossInfer，引擎管理服务用该二进制执行独立 `hello(devices: true)`，按 UUID 对齐设备并读取引擎支持状态、SM 能力与可用显存。旧版 probe 缺字段时保留 `unknown`，不可默认为支持。
4. 引擎安装/切换后，对新二进制重新做 probe，并与系统 inventory 交叉校验。SM75 包若未把目标 SM75 卡报告为支持，则禁止激活，并保留此前工作的引擎。
5. 窗口 focus、用户手动刷新、设备列表变化及任务启动前可触发刷新。运行态显存/利用率单独低频刷新，不重复启动完整引擎 probe。
6. 探测失败要将错误和采集时间暴露给 UI；不得返回成功形状的空清单。

系统层能力若无法在无引擎状态下取得，显示 GPU 已发现但“计算能力待引擎验证”。此时提供明确架构选择和对应资产清单，不推断未知卡为 SM80+。

### 4.3 默认 GPU 决策

自动推荐只在**本地 MossInfer 支持的 NVIDIA 卡**中选择，建议排序：

1. 当前候选引擎明确支持的卡优先于不支持/未知的卡。
2. 可比较的硬件性能字段优先（如 SM 数量 × 时钟等可靠探测值）；字段不可得时使用 SM 能力、型号档位和总显存构成的保守排序，并在 UI 标明这是估算。
3. 性能档相同，按总显存较大者优先。
4. 同型号、同能力、同显存时按系统 CUDA index 从小到大，保持可复现。
5. 当前可用显存低只影响“此刻是否适合启动”和建议，不改变持久默认卡，不把用户任务静默移到另一张卡。

自动结果只作为默认项；设置页允许选“自动推荐”或任意兼容卡。若无兼容卡，明确显示无本地可用设备，链接到引擎页；不默默选 CPU 或另一张架构不兼容的卡。

## 5. 架构感知引擎安装与激活

### 5.1 安装选择

引擎页的“GPU 架构”选择支持：

- **自动推荐**：由硬件 inventory 独立于当前引擎进行判断；多卡时展示将为哪些 GPU 下载兼容包。
- **标准架构**：选择上游常规包。
- **SM75**：选择上游 `-sm75` 包；若设备平台/Release 未提供该资产，直接说明不支持，不回退普通包。

Release asset 必须精确匹配版本、操作系统、CUDA flavour、打包类型和架构后缀。不得用“名字接近”的普通包兜底。CI artifact 同样要求明确匹配 SM75 构建产物。

### 5.2 多架构机器

MossInfer build 可以只包含某一架构，也可能包含多个架构。引擎资产清单和 hello 必须准确反映真实支持集合。

- 一份引擎支持所有选定 GPU：可共享该引擎程序，但运行时仍按每卡独立 sidecar/资源槽执行。
- 引擎只覆盖部分 GPU：只将已验证的 GPU 标记可调度；其余卡需安装匹配构建或选择自定义引擎。
- 若上游分别提供标准与 SM75 构建，应用应允许每个 GPU 绑定不同兼容引擎，而不是以“当前引擎”全局路径覆盖所有卡。
- 自动安装可按兼容分组准备一个或多个引擎，但在多资产/多次下载前必须展示预计下载项与磁盘占用。首次落地可以先实现单个 GPU/单个架构资产，并将混合架构标为下一阶段；任何阶段都不得将不兼容资产激活。

切换前验证 protocol、架构列表和目标 GPU 支持情况；验证成功后才持久化并重启对应 GPU runtime。更新失败保留旧版本和当前选择。

## 6. 显存与性能建议

### 6.1 建议输入

- GPU 的 SM 能力、总显存与探测时间。
- 用户显式选择的 engine tier、memory mode 和生成参数。

显存策略仅依据总显存选择预设：低于 6 GiB 为省显存，6 GiB 及以上为均衡，24 GiB 及以上为速度优先。实时显存只用于设备状态展示，不用于预测任务是否会显存不足，不写入长期默认偏好，也不触发自动调精度。

### 6.2 建议输出及边界

向用户推荐可读的性能/显存预设，例如“省显存 / 平衡 / 速度优先”，映射到现有 MossInfer memory mode，必要时附带 engine tier 建议。不显示任务显存估算或失败风险提示。

自动采纳范围只包括适用的执行/显存管理选项。**禁止**修改或替换：

- DiT、Text Encoder、VAE 等模型或 bundle；
- BF16/FP16/INT8/INT4 等模型权重精度、量化或 runtime dtype；
- 用户已经选定的 MossInfer tier，除非用户确认推荐；
- Canvas 的 `profile`、宽高、步数、CFG、seed 和 prompt。

OOBE 首次自动应用建议时显示“将采用 X 显存策略；不会更改模型或精度”，允许应用建议、手动选择或稍后处理。旧用户已有明确设置视作用户偏好，不在升级/每次启动时静默覆盖。

## 7. 持久化与 Canvas 绑定

### 7.1 应用设置

建议新增的设置字段：

```ts
gpuSelection: 'auto' | { uuid: string }
gpuProfileMode: 'auto' | 'custom'
gpuProfileOverrides: Record<string, {
  memoryMode?: 'min_memory' | 'balanced' | 'max_speed'
  tier?: 'reference' | 'high' | 'turbo'
}>
```

设置保存在现有 `settings.json`，通过 partial IPC schema 更新。旧设置迁移为 `gpuSelection: 'auto'`；迁移不可把过去保存的 `cuda:N` 当 UUID。

用户显式保存 per-GPU 覆盖后，即使设备不在线也保留该偏好；UI 显示“设备未连接”，不删除或改绑。

### 7.2 Canvas 与 Job

- Canvas 新增可选 `deviceUuid`（null/缺省表示提交时使用应用默认设备），并可显示已解析的型号摘要；摘要仅用于可读性，不代替 UUID。
- Result Canvas 默认继承来源 Canvas 的设备 UUID；复制参数新建 Canvas 时复制显式设备绑定。设备不可用时要求用户重新选择，不静默换卡。
- Job 在创建时快照 `deviceUuid`、当时解析的 `cudaOrdinal`、GPU 型号/SM、引擎版本和生效的 memory/tier 设置，用于重启恢复与诊断。
- 任务开始前重新校验 UUID 存在、引擎支持、显存可用性及模型绑定。队列等待期间若 ordinal 变化，以 UUID 重新解析；如果 UUID 消失则失败并提示重新分配，不把 `cuda:0` 指向新卡。
- 一个 Canvas 同时最多有一个活动推理任务；同 Canvas 的重跑也遵守其 GPU 槽位约束。

## 8. 按 GPU 的调度与并发

### 8.1 并发规则

- 每张本地 NVIDIA GPU 一个推理资源槽，同一时刻最多一个生成任务持有该 GPU 的槽。
- N 张**已发现、已启用、引擎兼容且可调度**的 GPU，最多 N 个本地推理任务并行；训练等非 MossInfer GPU 工作是否共享槽位需纳入活动利用率/冲突提示，不能假设 GPU 空闲。
- 用户明确绑定的 Canvas 只排入对应 GPU 队列。绑定卡忙则等待该卡，不擅自迁到其他 GPU。
- 自动绑定 Canvas 在提交时由调度器读取当前引擎的兼容 probe，优先选择推荐顺序中的空闲兼容卡；所有兼容卡繁忙时选择负载最低者，并立即固定 UUID，之后排队期间不漂移。
- 全局显示各 GPU 的运行任务数、等待数和槽位占用。取消、失败、引擎退出、应用关闭时可靠释放槽位。

### 8.2 Engine Runtime

已按 GPU UUID 将单例 MossInfer child、单一 `active`/`queue` 拆分为独立 runtime 状态：

- 每个 GPU UUID 有独立 runtime/sidecar、请求表、已加载模型 key、活动 generation 和队列。
- 每个 runtime 仅执行绑定给本 GPU 的任务；启动时把稳定 UUID 约束到进程可见设备，再使用该进程内可见 ordinal（通常为 0）。传递给引擎的 ordinal 必须由 runtime 建立并验证，不能直接使用系统 index。
- 每个 GPU runtime 可按需加载模型；相同 bundle 在多卡上会占用各自显存。当前提交时会显示单任务的模型体积/分辨率经验预检；并行任务合计显存成本提示仍待实现。
- 一个 GPU 内 FIFO；不同 GPU 的 FIFO 可同时推进。应用资源槽按 UUID 隔离，提交任务时 Canvas 绑定即固定，不会在队列等待期间漂移。
- 两个项目/窗口的 Canvas 共享相同 GPU 槽位管理器，不能通过不同 UI 绕过限额。
- 远端引擎 runtime 仍以 host + remote UUID 为独立资源域；首期可维持远端串行，不计入本机并发卡数。
- **连跑重载**（`mossInferRefreshEvery`，默认每 5 张，0 = 关闭）：一批图跑久了会变慢，原因不是泄漏——8 GiB 卡装不下 bf16 的 DiT（约 10.15 GiB），每一步都要从权重文件重读 20 多个 block；这些文件一旦被系统从页缓存里挤出去，每步拷贝从约 0.8 秒涨到 2.5 秒以上（日志里的 `cold: disk`）。每 N 张结束后先 `shutdown` 掉 sidecar（顺带释放 arena），下一张重新 `load`，既把权重读回缓存，也把显存归还；代价是每次多一次加载。设置页 `引擎 › 性能 › 连跑时重新加载引擎`。

## 9. UX/UI

### 9.1 启动检查与 OOBE

- 启动后后台扫描 GPU，主窗口先显示轻量“正在检测设备”，检测完成后更新，不阻塞启动。
- OOBE 准备清单新增“推理设备”卡片：GPU 数量、默认卡、SM、显存、兼容状态、推荐显存策略及“接受/自定义”入口。
- 多卡时默认选中的卡有明确标记；用户可展开所有卡并指定默认 GPU。若硬件扫描不完整，可重试。
- 无 NVIDIA GPU、无驱动、无引擎、引擎不兼容分别展示不同状态和下一步操作。
- 首次生成前再确认最终设备与策略；OOBE 跳过不影响手动配置，也不锁死工作台。

### 9.2 引擎页

页面顶部新增“本机推理设备”概览：每卡名称、UUID 短码、CUDA index、SM、总/可用显存、支持状态、占用状态和刷新时间。

每卡提供：

- 设为默认 / 自动推荐；
- 当前已激活引擎对该卡的兼容状态与 probe 原因；不同 GPU 绑定不同引擎版本仍未实现；
- 推荐显存策略及依据；
- “测试设备与引擎”操作和最近 probe 结果。

引擎下载区根据选中的 GPU 集合呈现架构选择和预期资产。例如 RTX 2080 检测为 SM75 时，自动推荐必须明确显示 `...-sm75...`；Release 没有该资产就禁用下载/提示自定义引擎，不能回退普通包。

### 9.3 Canvas

- 编辑面板显示“目标 GPU”选择器及兼容/显存提示；新 Canvas 使用应用默认 GPU，用户可逐 Canvas 改绑。
- Canvas 卡片显示已绑定 GPU 名称/显存、等待槽位时显示排队位置，运行时显示 GPU 和阶段进度。
- 对当前仍在排队、启动或运行的 Layout Canvas，左侧“开始生成”按钮保持禁用；任务失败或取消后根据 Job 终态恢复可用，成功后也允许再次提交。
- 运行中锁定设备绑定；取消后才允许改绑/重排。
- 自动分配也要显示具体分配结果，不能只写“自动”。
- 选择器仅列出当前已兼容 GPU；不兼容卡可展开查看原因，但不可提交运行任务。

### 9.4 顶部标题栏

在中间品牌标题之外，使用现有空余空间显示紧凑推理状态：

`RTX 2080 · SM75   GPU 62%   VRAM 6.1/8 GB   1/1 运行`

- 多卡时显示默认卡摘要与总活动任务数；可点击弹出卡片列表，展示各卡显存、GPU 使用率、绑定任务和队列。
- 没有运行时显示默认 GPU 名称、显存和推荐/自定义策略；设备探测中、无卡或不兼容时显示明确状态。
- 更新频率建议 2–5 秒；窗口隐藏/休眠时降频，任务结束后停止高频刷新。
- 由主进程统一采集并通过一个 IPC/event 快照广播，避免每个标题栏组件独立调用 `nvidia-smi`。
- 状态只显示本机 GPU 推理，不把远端卡的利用率混入本地数值。

## 10. 错误与恢复

| 场景 | 行为 |
|---|---|
| 自动检测不到 SM 能力 | 显示待确认；禁止自动选标准包，允许刷新、手选架构或自定义引擎 |
| SM75 资产缺失 | 保留当前引擎并显示缺失的精确资产名；不回退到标准包 |
| 下载包 hello 不支持目标 GPU | 安装不能激活；隔离/清理新目录，保留现有版本并报告 probe 结果 |
| UUID 在排队期间消失 | 将任务置为设备不可用失败，释放槽位并提供重绑操作 |
| UUID 仍在但 index 改变 | 按 UUID 重新映射；UI 更新 index，不改变 Canvas 绑定 |
| 显存状态 | 展示驱动遥测的实时显存占用；不预测任务显存需求或显示任务级估算提示 |
| 第二卡模型加载失败 | 只失败该 GPU 任务，不杀掉其他卡的 runtime |
| GPU reset / sidecar crash | 只终止并恢复对应 runtime；其队列任务显式失败或按安全策略重试一次，不重复已完成输出 |
| 老 Canvas 缺设备 UUID | 采用应用默认设备并在提交时固定；保存后写入 UUID |
| 多进程/多窗口提交竞态 | 主进程资源租约原子获取；同一 UUID 只能有一个活动 lease |

## 11. 分阶段实现与验收

### Phase 1：统一探测与安全选包

- 建立 GPU inventory IPC/event、UUID/SM/VRAM 展示。
- 启动时扫描；OOBE 与引擎页选择默认设备。
- 以硬件 inventory 选择架构；精确匹配并验证上游 SM75 资产，绝不标准包兜底。
- 持久化默认 GPU 和显存策略；加入迁移及多卡/缺字段测试。

**验收**：RTX 2080 自动选择 SM75 asset；一张 RTX 2080 + 一张 SM80+ 卡能分别显示能力；无引擎首次启动也不错误归为标准架构。

### Phase 2：Canvas 设备绑定与单卡资源槽

- 已完成：Canvas/Job 使用 GPU UUID；旧 Canvas 缺字段时跟随应用默认；提交任务时固定 UUID 与设备快照；主进程阻止同一 Canvas 重复活动任务；Studio 可为 Canvas 选择 GPU。
- 已完成：主进程按 GPU UUID 维护独立资源槽，Engine Manager 为每卡维护独立 sidecar 和 FIFO；同卡串行、不同卡可并行；卡片显示 GPU，排队序号按资源槽计算。

**当前验证**：UUID 解析使用当下 inventory ordinal；缺失的已绑定 GPU 不会静默改绑。自动化构建/fake server 通过；由于当前开发机只有一张 NVIDIA GPU，双卡并行硬件验收仍未完成。
**最终验收**：1 GPU 时两个 Canvas 只能一个活动；2 GPU 时不同卡可同时活动、同卡仍串行；UUID 与 ordinal 变化后不会错绑。

### Phase 3：性能推荐、OOBE 与标题栏

- 已实现：按总显存给出省显存/均衡/速度优先建议；设置支持每 GPU memory mode/tier 覆盖。任务提交时解析并快照实际配置，且仅覆盖 MossInfer 的 memory mode/tier，不改模型、dtype、精度或 Canvas 参数。
- 已实现：OOBE 与引擎页显示单卡建议并允许用户应用；未确认的建议不会静默覆盖已有设置。
- 已实现：主进程统一采集每卡显存/利用率与本机运行/排队任务数，通过单一 telemetry event 广播；窗口可见时有任务约 4 秒更新、空闲约 15 秒，隐藏约 30 秒，系统挂起期间暂停。
- 已实现：Studio 标题栏展示默认 GPU 状态，展开后查看各卡显存、SM、利用率、任务队列及有效显存策略。
- 仍待硬件验收：当前单卡开发机不能验证真实异构双卡并行及占用变化；系统恢复后的采样由 resume event 立即触发。

**验收**：重新启动后记住用户 GPU/策略选择；探测信息缺失时不误报；动态占用变化及时但不抖动；不触碰模型精度和 Canvas 参数。

### 自动化与硬件验收矩阵

- 单卡 SM75、单卡 SM80+、异构双卡、同型号双卡、无 NVIDIA、无引擎、引擎 probe 字段缺失。
- Release 资产存在/缺失、普通包与 `-sm75` 后缀匹配、错误资产 probe 拒绝激活。
- 设备 UUID/index 变化、设备拔除、调度并发竞态、取消/崩溃释放资源槽。
- 性能策略迁移与持久化；断言 dtype、bundle、quantization、Canvas 参数未变化。
- Windows RTX 2080 真实出图及至少一台 SM80+ GPU 真实出图；异构双卡并行压测记录每卡显存峰值。
