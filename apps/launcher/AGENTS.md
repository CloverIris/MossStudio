# apps/launcher

The Go launcher, setup stub and uninstall finisher for Windows and Linux. One binary, several modes; `main.go` lists them. The root [AGENTS.md](../../AGENTS.md) applies here too; this file adds what is specific to Go and to this binary.

## Commands

```bash
cd apps/launcher
gofmt -l .                               # must print nothing
go vet ./... && GOOS=windows GOARCH=amd64 go vet ./...
go test ./...
./build.sh                               # both binaries into dist/, version from apps/desktop/package.json
```

Changes here trigger the package + install/update/rollback matrix in CI. Run `pnpm test:install` from the repo root before opening the PR.

## Rules

- Standard library only. `go.mod` has no `require` block; keep it that way.
- `CGO_ENABLED=0`. Both binaries build from any host; do not add anything that needs a C toolchain or a platform SDK.
- Code that calls a platform API goes in a file with a build suffix (`_windows.go`, `_linux.go`, `_unix.go`, `_other.go`) with a matching stub for the other platforms. A `runtime.GOOS` check is fine for a small behavioural difference in portable code. Both `go vet` runs above must pass.
- The Windows binary is a GUI-subsystem executable: nothing written to stdout or stderr is seen. User-facing messages go through `internal/ui`.
- Tests run on Linux in CI. Windows-only behaviour needs a test that runs on Linux (pure functions, fakes) or coverage by the install matrix.
- `rsrc_windows_amd64.syso` is generated by `build.sh` and is ignored by git. Do not commit it.
- The launcher version comes from `apps/desktop/package.json`. Do not add a second version constant.
- Every child process the launcher starts is either waited on or deliberately detached (`internal/proc`); a wait on another process has a timeout and a fallback.
- Comments say why, not what. gofmt owns formatting.
