# MOSS-Image model notes

The facts about the MOSS-Image files that MossStudio and its engine depend on: component sizes, the DiT structure, sequence lengths and compute per image, memory budgets by device class, the samplers, and the numeric conventions that must be kept. Every number comes from the published checkpoints' configs and index files or from upstream code, with its source; the budget tables are generated by `python3 tools/dev/budget.py --markdown`.

How the files are downloaded, stored and handed to the engine is in [`models.md`](/docs/reference/models.md). What the engine does with them is in the [MossInfer repository](https://github.com/mossimage-cpp/mossimage.cpp).

## 1. Components

| Component | Class | Parameters | bf16 | Structure |
| --- | --- | ---: | ---: | --- |
| DiT | `MOSSImageTransformer` | 5.082 B | 10.16 GB | 42 single-stream layers, dim 3072, FFN 8192, 24 heads |
| Text encoder | `Qwen3_5Model` | 8.393 B | 16.79 GB | 32 layers: 24 linear attention plus 8 full, hidden 4096 |
| VAE | `AutoencoderKLFlux2` | about 0.125 B | 0.25 GB | 32 latent channels, 8x spatial, 2x2 patch, 16x in total |
| Scheduler | `MOSSImageScheduler` | | | Euler, shift 5, 1000-step training grid |

Sources: [transformer/config.json](https://huggingface.co/OpenMOSS-Team/MOSS-Image-Base/raw/main/transformer/config.json), [text_encoder/config.json](https://huggingface.co/OpenMOSS-Team/MOSS-Image-Base/raw/main/text_encoder/config.json), [vae/config.json](https://huggingface.co/OpenMOSS-Team/MOSS-Image-Base/raw/main/vae/config.json), and `metadata.total_size` of the two `*.index.json` files.

The VAE config says `latent_channels: 32` and the DiT config says `latent_channels: 128`. Both are right: 128 = 32 x 2 x 2 after patchifying. The DiT's height and width are the pixel size divided by 16.

Weight sizes at other precisions (`budget.py`, "Weights"):

| Component | Parameters | bf16 | int8 | int4 |
| --- | ---: | ---: | ---: | ---: |
| DiT | 5.082 B | 10.16 GB | 5.08 GB | 2.54 GB |
| Text encoder (Qwen3.5-9B) | 8.393 B | 16.79 GB | 8.39 GB | 4.20 GB |
| VAE | 0.125 B | 0.25 GB | 0.12 GB | 0.06 GB |
| Total | 13.600 B | 27.20 GB | 13.60 GB | 6.80 GB |

## 2. DiT structure

Checked item by item against the upstream code:

- `video_embedder`: Linear 128 to 3072, one token per point of the /16 grid.
- `text_embedder`: Linear 4096 to 3072, then two `_TextBlock`s (fused qkv, qk-norm, RoPE, SiTU FFN, no modulation).
- `time_embedding`: sinusoid(256), Linear, SiLU, Linear, with fp32 weights.
- `shared_block_modulation`: one Linear 3072 to 6 x 3072, shared by all 42 layers.
- `layers.0..41`: joint blocks over the sequence `[image tokens ; text tokens]`. RMSNorm and modulation, q/k/v, per-head qk RMSNorm and 4-axis RoPE, attention, gated residual, RMSNorm and modulation, `ffn_up_gate` (first half up, second half gate), SiTU, `ffn_down`, gated residual.
- `final_norm_video`, `video_head_modulation`, `final_linear_video` (3072 to 128).
- The output is a flow velocity: `v = noise - x0`, sigma in [0, 1], 1 being pure noise.

SiTU: `(4 * tanh(g/4) * sigmoid(g)) * (25 * tanh(u/25))`, no parameters; it decomposes into sigmoid, tanh and multiply.

RoPE (4 axes): coordinates `(r, f, h, w)`. Image tokens have `r = 0`, `f = text_len`, and `h, w` centred (minus `(size - 1) / 2`); text tokens have `f = position` and 0 elsewhere. The number of frequency bands is `head_dim / 8` = 16; each coordinate gets 16 frequencies, `sin` and `cos` make 32, and the four axes make 128 = `head_dim`. The tables are precomputed on the host and passed as a graph input, so the graph holds no dynamic trigonometry or grid generation.

## 3. Sequence length and compute

Per DiT forward, with 256 text tokens (`budget.py`, "Sequence length and FLOPs per DiT forward"):

| Resolution | Image tokens | Sequence | Linear | Attention | Total |
| --- | ---: | ---: | ---: | ---: | ---: |
| 512 x 512 | 1024 | 1280 | 13.0 TF | 0.8 TF | 13.9 TF |
| 768 x 768 | 2304 | 2560 | 26.0 TF | 3.4 TF | 29.4 TF |
| 1024 x 1024 | 4096 | 4352 | 44.2 TF | 9.8 TF | 54.0 TF |
| 1280 x 768 | 3840 | 4096 | 41.6 TF | 8.7 TF | 50.3 TF |
| 1024 x 1376 | 5504 | 5760 | 58.5 TF | 17.1 TF | 75.7 TF |

The attention share grows with the square of the resolution: 18% of the total at 1024², 23% at 1024 x 1376. Flash or blocked attention is required from 1024² up.

End to end, text encoding and VAE decoding included (`budget.py`, "End-to-end time by device"; `base-50` is 50 steps with CFG 3, `dmd-8` is the 8-step DMD profile):

| Device | 512² base-50 | 512² dmd-8 | 1024² base-50 | 1024² dmd-8 |
| --- | ---: | ---: | ---: | ---: |
| M4 Max 40c (measured, MLX bf16) | 90 s | 8 s | 5.8 min | 29 s |
| M1 Max 24c (measured, MLX bf16) | 4.3 min | 22 s | 16.8 min | 83 s |
| M3 10c (estimate) | 8.8 min | 45 s | 34.3 min | 2.8 min |
| RTX 4090 (estimate) | 25 s | 2 s | 1.6 min | 8 s |

Calibration point: M4 Max with MLX, 1024², 50 steps, CFG 3, bf16 = 358 s (mlx-serve PR #908), which implies about 15.3 effective TFLOP/s and matches the budget model. The estimates are scaled from that number, not measured; MossStudio's own measurements with MossInfer are in [`records/2026-10-31-mossinfer-1.0.0-performance.md`](/docs/records/2026-10-31-mossinfer-1.0.0-performance.md).

## 4. Memory budgets

Budget profiles by device memory (`budget.py`, "Memory profiles"). They assume staged loading: the text encoder is unloaded once the prompt is encoded, then the DiT is loaded, and the DiT is unloaded before decoding.

| Device memory | Text encoder | DiT | VAE | Weights resident |
| --- | --- | --- | --- | ---: |
| 8 GB | int4 | int4 plus block streaming | int8 | about 7.0 GB |
| 16 GB | int4 | int8 | int8 | about 9.8 GB |
| 24 GB | int8 | int8 | int8 | about 13.6 GB |
| 48 GB and more | bf16 | bf16 | bf16 | about 27.5 GB |

Staging is a hard requirement: all three components resident in bf16 (27.2 GB) on a 16 GB machine must swap. Weight-only int8 and int4 reduce memory traffic, not the FLOP count. These are planning budgets; the tiers MossInfer runs and how the app chooses them are in [`engines.md`](/docs/reference/engines.md).

## 5. Samplers

### base (official)

```
sigma grid: lower = shift / (1000 + shift - 1)
values = linspace(1, lower, N)
sigmas = shift * values / (1 + (shift - 1) * values)
then snap to the nearest point of the 1000-step training grid and deduplicate
```

- Defaults: 50 steps, CFG 3, `shift = 5`.
- The negative branch skips block 22. This is not a cheaper CFG: the skip prediction replaces the negative prediction, and there are still two forwards per step.
- CFG is combined in fp32 (an explicit upstream comment).
- The initial noise is sampled in fp32; sampling in bf16 and upcasting does not recover the precision.

### dmd8 (community distillation, optional profile)

[lodestones/MOSS-Image-SFT-8-steps-dmd](https://huggingface.co/lodestones/MOSS-Image-SFT-8-steps-dmd) (Apache-2.0): data-space DMD, 8 forwards, no CFG, fp32.

```python
Q, codes = load("dataspace.safetensors")      # Q: [128,128], codes: [8]
z = randn(1,128,H//16,W//16, fp32); x0 = zeros_like(z)
for r in range(8):
    x = z + einsum("oc,bchw->bohw", Q, x0)
    v = dit(x, codes[r], embeds, mask)        # fp32
    x0 = z - v
decode(x0)
```

The accompanying `time_embedding.safetensors` is a replacement (it includes `shared_block_modulation.bias` and `video_head_modulation.bias`) and must be fp32; `lora.safetensors` is a rank-128 delta. All three files are required. In the catalog these are the `kind: 'dmd'` adapters `dmd8-sft` and `dmd8-base` with `requires_profile: 'dmd8'`.

## 6. Numeric conventions

Copy these exactly; deviating shifts the image quality.

| Where | Precision | Why |
| --- | --- | --- |
| Timestep sinusoid | computed in fp64, stored fp32 | Upstream trained this way |
| `time_embedding`, modulation | fp32 weights and outputs | Small modules whose error 42 layers amplify |
| CFG combination | fp32 | Upstream comment: converting only the final velocity keeps rounding error |
| Initial latent | fp32 | bf16 noise cannot recover the precision |
| VAE | fp32 (upstream `force_upcast`) | Decoding is precision sensitive |
| DMD | all fp32 | The distilled delta is smaller than bf16 rounding |

## 7. Weight layouts

| Source | Keys | Handling |
| --- | --- | --- |
| HF diffusers `transformer/` | `layers.N.proj.q.weight` and so on | Direct mapping |
| ComfyUI single file | no prefix, or `model.diffusion_model.` | Strip the prefix; split `proj.qkv` into q, k, v |
| Comfy-Org repack | fused qkv | Split, then load |
| KohakuMoss single file | bare keys | Readable as is (the format is public) |

`rope.bands` is a derived buffer and can be recomputed instead of loaded.

## 8. Known pitfalls

1. VAE memory: decoding 1024² without tiling runs out of memory (25.5 GiB of intermediate activations measured).
2. Text encoder: upstream `encode_prompt` runs one forward per prompt. Padding pollutes the linear-attention state of Qwen's GDN layers, so an engine must bucket by true length and never pad a whole batch.
3. Batches: upstream loops over samples for the DiT (each sample uses its own text mask); batched generation must not stack them naively.
4. CFG and skip: the skip applies only in `slg_start..slg_stop`, the whole range by default.
5. Resolution: width and height must be multiples of 16, otherwise upstream raises.

## 9. Community FP16-fixed weights (KBlueLeaf)

Source: [KBlueLeaf/MOSS-Image-FP16-fixed](https://huggingface.co/KBlueLeaf/MOSS-Image-FP16-fixed), Apache-2.0, commit `a880990b7fc9d2052f32fa9a1527f524b6847e83` (2026-10-19).

### 9.1 What it is

- It replaces only the transformer, with separate DiT weights for Base and SFT. The text encoder, tokenizer, VAE, scheduler and pipeline code stay the official ones.
- The official weights' residual stream peaks at about 61 to 62 k, close to the fp16 limit of 65.5 k (about 1.05x headroom). The fix scales the stream in the weights by `c = 1/16`, giving about 16.9x headroom at the same point.
- The scale is a power of two, so it is exact in fp32 and bf16; RMSNorm `eps` keeps the official value, and diffusers and ComfyUI load it unchanged.
- The model card calls it "same outputs as the official model up to rounding" and reports it closer to fp32 than the official bf16 in its own tests. That is not a proof of higher precision in every case.

### 9.2 Files and sizes

| Content | Path | Size |
| --- | --- | ---: |
| Base transformer (diffusers, 3 shards plus config and index) | `base/transformer/` | 10.16 GB |
| SFT transformer (diffusers) | `sft/transformer/` | 10.16 GB |
| Base ComfyUI single file | `comfyui/moss_image_base_fp16_fixed.safetensors` | 10.16 GB |
| SFT ComfyUI single file | `comfyui/moss_image_sft_fp16_fixed.safetensors` | 10.16 GB |

The whole repository is about 40.7 GB (two diffusers sets, two ComfyUI files, reports and images). The catalog (`apps/desktop/resources/models.json`) splits it into four `role: 'dit'` entries, `moss-base-fp16-fixed`, `moss-sft-fp16-fixed`, `moss-base-fp16-fixed-comfy` and `moss-sft-fp16-fixed-comfy`, each downloading only its own files (about 10.16 GB). The four share one repository cache; downloading one does not fetch the others, and deleting one removes only that entry's record. The diffusers entries still need the official text encoder, VAE and tokenizer, which the `moss-sft-fp16` and `moss-base-fp16` bundles provide; the ComfyUI entries are download only (see [`models.md`](/docs/reference/models.md), section 8).

### 9.3 Quality and hardware notes

- The model card reports (RTX 5090, 1024², 50 steps, CFG 3, against each pipeline's own fp32 reference): ComfyUI Base fp16-fixed LPIPS 0.0062 / PSNR 44.8 dB versus official bf16 0.0501 / 29.3 dB; SFT 0.0042 / 43.2 dB; diffusers Base 0.0111 / 42.8 dB versus official bf16 0.0900 / 26.8 dB. These are the author's measurements, not this project's.
- Only the transformer is replaced. A LoRA or LoKr that touches `video_embedder`, `text_embedder` or `shared_block_modulation` needs its delta scaled by the same `c`; adapters on the usual q, k, v, o and FFN weights transfer unchanged.
- It needs the official model's text encoder, VAE and tokenizer; it is not a complete pipeline on its own.
